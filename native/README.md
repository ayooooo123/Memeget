# Memeget Native

Memeget's native Android app uses Kotlin, Compose, SQLite and a JNI inference adapter. Application ID: `com.memeget.nativeapp`; launcher label: **Memeget Native**. It installs alongside any existing legacy React Native install, but does not replace that app's package, database or private files. The legacy source has been retired; see Local use and migration for importing an existing library.

Every push to `main` builds a release APK in GitHub Actions (`../.github/workflows/release.yml`), runs the host tests first, and publishes it as the rolling `latest` release: https://github.com/ayooooo123/Memeget/releases/download/latest/memeget-latest.apk. The same workflow adds the iOS IPA to that release. Tags `vX.Y.Z` publish permanent releases. Evidence so far and the checks still open are listed under Verification record.

## Build

Build from this directory, within the repository checkout. The build compiles an explicit allowlist of reusable Kotlin media utilities and fonts from `../modules/memeget-bg/android/src/main` into generated build directories. These are plain native sources; the old Expo module wrapper and React Native application are no longer included.

Requirements:

- JDK 17. The included wrapper pins Gradle 8.14.3 and its distribution SHA-256.
- Android SDK platform 36, Android platform tools, NDK `27.1.12297006`, CMake `3.22.1`.
- `ANDROID_HOME` pointing to the SDK, or an untracked `local.properties`.
- Network access for Maven dependencies and the checksum-pinned runtime archive.

```sh
./gradlew :app:assembleDebug :app:testDebugUnitTest
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

Only ARM64 is packaged; minimum Android version is API 26. `runtime/bootstrap.sh` extracts the pinned `react-native-executorch@0.9.2` C++ dependencies into an ignored build cache after SHA-512 verification. This reuses the native runtime, not its React Native application layer. Model files are downloaded separately on demand and must match the sizes and SHA-256 digests in `app/src/main/java/com/memeget/nativeapp/inference/ModelRegistry.kt` before activation. A stopped download keeps what arrived and resumes with a range request the next time a feature needs the model. **Settings → On-Device Models** lists each model as downloaded, downloading, paused at a percentage, failed, or not downloaded yet.

`./gradlew :app:assembleRelease` builds `app/build/outputs/apk/release/app-release.apk` for everyday use; the published releases are this build. It is signed with the key the original app pins in `../signing/debug.keystore`, so each release installs over the last one and keeps the library. It is not debuggable: no keep-awake flag and no `run-as` access to its database. Debug builds are signed with the build machine's own debug key, so a release and a debug build cannot replace each other; switching means uninstalling first, which deletes that install's library. The version comes from `../version.xcconfig`, shared with the iOS app: version name `X.Y.Z` and version code `X*10000 + Y*100 + Z` (1.1.0 is 10100). Android refuses to install a lower version code over a higher one, so going back to an older release, including any build from before 1.1.0 (version code 1), means uninstalling first. Builds between tags share a version, so a release's version name also ends in the commit it was built from (`1.1.0-dcfc836`), shown at the bottom of Settings, so two releases can be told apart.

Debug builds are much slower in the UI: on the Pixel 5a, flinging the library dropped 32% of frames (p99 550 ms) on a debug build and 0.5% (p99 32 ms) on a release build of the same commit, and a cold start took 1.7 s against 0.9 s. A phone that holds a debug install gets release speed, library intact, from a release build signed with the same machine's debug key, installed over it: `./gradlew :app:assembleRelease -Pandroid.injected.signing.store.file=$HOME/.android/debug.keystore -Pandroid.injected.signing.store.password=android -Pandroid.injected.signing.key.alias=androiddebugkey -Pandroid.injected.signing.key.password=android`. It has no `run-as` until a debug build from that machine goes back on, again in place. Don't publish that APK: it is not signed with the repository key.

Build policy for the owner's phones: the dedicated test phone, a Pixel 5a, stays on debug builds, so its database stays readable with `run-as`; only the everyday phone, a Pixel 9, gets release builds. The 5a's debug build is the slow floor: what feels fine there should feel fast on a recent phone with a release build.

## Local use and migration

- Link a folder with Android's document picker, or import/share media, supported links, ZIP collections or teaching files. Temporary shared content is copied into private storage before its temporary permission expires.
- Sharing an Imgflip `/memegenerator/<id>` or `/memetemplate/<id>` link saves the full-size blank template from its template page without the Imgflip watermark (for example, `https://imgflip.com/memegenerator/129385783/Do-you-see`); a finished `/i/<id>` post saves its published image, including any watermark already baked into it.
- Browse immediately while analysis is pending. Waiting tiles show **Queued**; only the coordinator's active meme animates **Analyzing**. Failed indexing has a persisted **Analysis failed** status, cleared by retry or successful analysis; tapping **Index** retries failed items along with pending ones, while background work does not. Search runs against a revision-synced resident RAM index (up to 6,000 items, streaming above that) plus a 64-entry LRU query-embedding cache: the lexical pass lands at 0 ms delay while typing, and the semantic pass fuses whole-word IDF-weighted text/tag coverage, modality-bridged `OpenVocabConcepts` prototypes, multi-scene/panel vectors, social-slang/reaction-intent cues (`SocialReplyIntent`: *"cooked"*, *"joever"*, *"copium"*, *"cinema"*, *"caught in 4k"*), pasted-post distillation (stripping `@handles`, links and conversational filler) and battle-tested copy frequency on MobileCLIP's cosine scale. Pagination uses stable keyset cursors, 2-letter terms (`ai`, `tv`, `fr`) stay live across both passes, and typo/prefix expansions from the `fts4aux` word list never hijack exact BM25 weights.
- The Library keeps its search, filters, loaded pages and scroll position while **Label** or **Settings** is open; Back on those tabs returns to it, and Back in selection mode clears the selection. Library writes (indexing, a re-tag) reload it after a short settle and never cancel a load under way, so searches finish and a deleted meme leaves the grid while work runs. Only a search you start pauses background work.
- The Library's floating switch picks **Grid**, **Canvas** or **Folders**, and remembers the choice. **Canvas** lays the current results (the whole library, a search or a filter) out as justified rows twice the screen's width: drag in any direction, fling, pinch out to see a whole row or in for detail, tap to open, long-press to copy. Each picture's shape is read from its file header once per app run, so tiles never move once placed. **Folders** shows up to 24 tags as stacks, each chosen to add the most memes no earlier folder holds (labels you taught are starred). Switching between Canvas and Folders flies the tiles on screen into their folders' stacks and back; opening a folder bursts its memes onto the canvas, and Back or the `←` pill sends them home. Selection, batch tagging and the scan button stay in Grid.
- The viewer shows the meme on a card over a blurred copy of itself. Swipe sideways for the next or previous meme in the list it was opened from (a look-alike opened from the viewer slots in right after the meme it came from); swipe down on the meme to close. The meme's details (actions, caption, OCR, transcript, tags, look-alikes) live in a sheet: swipe up on the meme or the bottom dock, or tap the title pill, to open it; swipe down or Back to close it. The dock keeps the title (the meme's best tag, else its caption) and a one-tap copy button on screen while you browse.
- **Folders** has four kinds of stack, each in its own section. **Tags** (above). **Quotes**: lines said in two or more clips (marked 🗣, from transcripts) and lines written on two or more memes (OCR), ranked by how many memes carry them times how rare their words are, so filler like "a lot of" drops out; a re-upload of the same clip doesn't count as a second quote. **Reactions**: the best 60 matches for each of 14 replies (agree, cope, cringe, W, L, shocked, smug, laughing, crying, angry, confused, I'm done, hype, sus). **Formats**: memes sharing one picture with different words (image cosine ≥ 0.86, OCR differs), groups of 3–120, named after a tag at least half of them carry.
- Near-copies (image cosine ≥ 0.97, same kind, same OCR text; two videos also need the same non-blank transcript, since the picture says nothing about the audio) show once, as the newest copy, wherever the kept copy is on screen too. Groups are worked out from the resident search index's int8 vectors, with a 512-bit sign-code prefilter, and cached until the index changes.
- Opening a video from a search or a spoken quote starts it a second before the line, placed by where the line falls in its transcript (transcripts carry no timings, so this is an estimate).
- Copying a meme remembers the search it came from; the same search afterwards ranks it higher (`copy_queries`, boost min(0.35, 0.18·ln(1+copies))), even if it wouldn't match otherwise.
- **More like this ▶** on the viewer's look-alikes section replaces the rest of the swipe list with the closest look-alikes, then keeps adding the look-alikes of whatever the list ends on, skipping memes already in it.
- A meme shared or imported while a session transcribes or captions is indexed once the clip in progress finishes, before the rest of that backlog; a background session still stops at its item cap.
- X's animated-GIF MP4s set the `ctts` box flags to 1, which Android's MP4 extractor rejects as malformed, so the platform can read neither frames nor a poster from them. Indexing zeroes those flags in its private working copy before reading frames and making the poster; originals are never modified and the content hash covers the original bytes.
- Every image and video frame reaches the image model and OCR as a 768-px-wide JPEG at quality 90, the way the original app prepared them, so natively computed vectors match its exports and teachings. This also covers WebP, GIF and HEIF, which the native decoder (OpenCV) cannot read; WebP is almost half of the images in one real library.
- Review tags, add positive/negative teachings, find similar images, and edit images or videos in Remix Studio. Image and video outputs are new files, never in-place changes to originals.
- The **Label** tab asks about the memes whose answers spread furthest: unlabeled memes with the most unlabeled look-alikes come first (at cosine ≥ 0.80 first, then broader template/character clusters at ≥ 0.68), and memes that already get a label on their own are skipped; a "not this" alone does not take a meme out. Each card shows the meme's confirmed tags (`✓ tag  ✕`) and rejections (`✗ tag  ✕`), offers up to three of your existing labels with **Yes** / **Not this**, and has a text field with autocomplete (`Add tag(s) — comma-separate for multiple`). Tapping a `✓` or `✗` chip removes that answer and its teaching from the meme; **Previous** returns to the last card. Adding a tag keeps regular cards open so you can attach several references to a composite meme (one by one or comma-separated) before tapping **Next meme**. Background captioning and transcription pause while the Label tab is open. Answers are teachings and finish saving even if you leave the tab mid-save. Leaving the tab re-tags the library so they spread, at once or as soon as running indexing ends. Cards asking whether a meme you labeled otherwise also shows a label come first when a few answers would let that label spread (see Identification). The look-alike counting behind the queue runs in native code (`cpp/VectorKernels.cpp`): on a Pixel 5a running the debug app the first card shows about 3 s after the first open and about 1 s after later opens (0.96–0.99 s over three screen recordings), where the Kotlin loops took 16–18 s. With the ask cards it took 2.29 s on a first open and 1.27 s on a later one (one recording each).
- Viewer **Copy meme** and each grid tile's top-right **1-tap `⧉` Copy pill** publish an image/video content URI to Android's clipboard (`…/clipboard/<n>/<name>.mp4`, no query string) and increment the item's copy history, surfacing battle-tested reply memes under the **`⚡ Used`** filter chip and nudging ties toward frequently sent reactions. Highlighting text in another app offers **Meme Reply** (`ACTION_PROCESS_TEXT`), sharing plain non-URL text routes straight into contextual search, and the search bar's **`📋`** button pastes a copied post in one tap. **Remix Studio → Export → Copy to Clipboard** copies the rendered result without adding a library item or discarding the editing project. Viewer WebM copies are converted to H.264/AAC MP4; other supported media are copied without re-encoding. The destination app must support pasting that media type: on the Pixel 5a a separate test app that accepts `video/*` received the full MP4, while a plain text field pasted nothing.
- Debug builds keep the screen awake only while the app's window is visible. Release builds and device lock security are unchanged; this does not bypass the lock screen or keep other apps awake.
- The editor includes text, drawing, crop/rotation/flip/aspect, OCR replacement, cover/pixelation, subjects, stickers, backgrounds, ordering and undo/redo. Video projects get the same crop/rotation/flip controls, with the whole source frame shown while the crop rectangle is dragged. Video composition supports retained ranges, speed/audio/music, title cards and time-aware overlays. Animated GIF export and automatic video subject isolation remain unsupported; manual motion/keyframes are supported.
- Keep the original app installed during migration. First make its latest folder backup, then link that folder in the native app. The backup matches files by name only, which can't vouch for the bytes, so its hand tags return as unconfirmed suggestions: indexing keeps them and they stay searchable, but they don't count as a person's labels for look-alike voting, and on a meme where the app itself suggests six or more tags they can be pushed out. Its teachings return and attach by image vector. To bring hand tags back as confirmed labels, also share the original app's collection ZIP (version 2); it can be shared right after linking. Imports match files by content: a library item a folder scan found but indexing hasn't reached yet has no hash, so an import hashes the unhashed items of the same size before copying anything, and a file already in the folder is used as it is, not written into the folder again.
- For a device move, use the original app's **Settings → Folder backup → Back up now**, then copy every linked folder including hidden `.memeget`, preserving names and layout. Compare backup coverage with the collection before assuming private/unlinked imports were included. **Export collection (zip)** version 1 contains resized JPEGs and video posters; version 2 preserves original image/video bytes and stored classification metadata, including tag scores. Re-export with the updated original app when full media is required. Native ZIP intake imports the media and, from `manifest.json`, what a person or the bytes vouch for: hand tags and teach-sheet labels (as confirmed hand tags), OCR and transcripts, matched to each file by archive path, including files already in the library. Machine predictions and captions are not restored. Version 2 exports also supply each item's image vector, so those items index without running the image or text models; version 1 previews do not, because their vectors describe the original files rather than the resized copies. An exported vector and OCR are reused only while the file still has the exported bytes (same SHA-256); a changed file is analyzed fresh. When the manifest cannot be read (over 2 GiB, or damaged) the media still import and the import reports that their labels did not. Preserve an immutable prediction/metadata snapshot before reindexing for an accuracy comparison.
- Native folder backups write only `.memeget-native`, by themselves as the original app keeps `.memeget`: 30 s after the library last changed (labels, teachings, captions, transcripts or other analysis), and at once when the app leaves the screen with changes not backed up yet. Each change during a long indexing session pushes the backup back, so it runs once the session goes quiet. Each linked folder's card in Settings also has **Backup** and **Restore**, and Settings shows when the last automatic backup finished. Generation-addressed chunks are written before the manifest, so an interrupted backup leaves the previous complete generation in place; once a new generation is committed, older ones are deleted except the newest complete one before it. The library is read for a backup while no restore, scan or import is running. After **Clear Index**, and while a folder's restore is unfinished, that folder's automatic backup pauses, so a library holding less can't replace the backup that still has the tags; **Restore** or **Backup** on the folder lifts the pause, and Settings says when one is paused. A folder whose backup fails is logged once, not on every retry. The legacy `.memeget` namespace is read-only.
- Sidecars do not transfer Android permissions, model downloads, private editor drafts, settings or credentials. Teaching files retain their declared model fingerprint; a vector from another recipe is not silently marked current. Native teaching files reject unknown schema versions and missing fingerprints. Teaching files can be shared to the app or picked in Settings. Each example attaches to the meme it shows (image vectors at cosine ≥ 0.985) when the teaching file is imported, when a collection is imported after it, and when indexing first gives that meme a vector: a "this is X" example becomes a confirmed tag there, and a "not X" example a rejection that also removes X from the meme's search text, cloud caption and terms included. A user's own tag on that meme is never overridden.
- The original `mobileclip-s2` teaching fingerprint is accepted after independent comparison of 32 images and eight texts against the original encoder recipe. It remains unchanged on import/export. Other foreign fingerprints are excluded from training. Encoder compatibility does not verify media identity: filename-only restores discard stored vectors and reviewed identities, preserve imported text, and require fresh indexing.
- **Delete**, in the viewer or for a selection, removes memes from the library and deletes their files from their folders (or the app's own copies), as the original app does. The meme leaves the library even when its file can no longer be deleted. Tapping **Index** rescans every linked folder for new files before it starts indexing, again as in the original app.

## Identification

People's labels spread to look-alike memes through a nearest-neighbour vote over image vectors (`LookalikeVote`). The references are taught examples and memes carrying a confirmed label; "not X" teachings and per-meme rejections are counter-examples. A meme gets a label when the winning label among its five nearest references has a reference at cosine ≥ 0.80 and no "not X" example of it is closer. Exact copies of a labeled picture always carry its labels.

A label applies on its own only after it held up on people's own labeled memes: each labeled meme is voted on with its own labels and copies left out, and a label needs at least three such votes, 90% of them right. Other labels stay suggestions for the Label tab until answers prove them. The vote has no training step; its index rebuilds only when people's labels, teachings or the vectors behind them change.

A vote for X on a meme someone labeled only with other labels counts as a miss, yet nobody judged it: people often tag what a meme shows rather than everything in it. When a few "Yes" answers on such memes would lift a label to 90%, the Label tab asks about them first ("You tagged this “tired”. If it is also pepe, 2 Yes answers like this let pepe label 59 look-alikes on its own."), labels that would then label the most unlabeled memes first. A "Yes" counts toward the label, and once it passes, or can no longer get there, its other cards go. A label that passes also reaches memes people labeled otherwise. The held-out votes and the winners for every unlabeled meme run through a native nearest-neighbour kernel (`LookalikeKernels.nearest`).

Measured on one real 2,370-meme library with the owner's 602 labeled memes split in half, each half's settings chosen on the other half: the vote agreed with his labels 89% of the time and labeled 27% of held-out memes, returning none of the labels he had rejected on them. Per-label logistic heads (the previous learner) labeled 28% at 57% agreement and returned 10 rejected labels; best-example retrieval labeled 79% at 20% agreement because it gives every meme five labels, so it now only ranks suggestions. Agreement here is with that owner's incomplete labels on memes he chose to label, not verified accuracy on the rest of a library.

That 27% does not carry over to the memes nobody labeled. In the same library only 139 of its 1,752 unlabeled memes have a labeled look-alike at cosine 0.80, and the vote labeled 25 of them. Eight Pepe memes tagged only "tired", "hug" and the like held pepe at 58 of 66 held-out votes, under the bar; once the owner approved tagging them pepe, the label passed at 69 of 70 and a re-tag gave it to 61 more memes, all of which show Pepe. The vote's labels then covered 86 memes.

Re-classification replaces the machine tags it recomputes (zero-shot prompts, learned look-alike labels, OCR rules, titles) instead of merging old ones back, keeps human-confirmed tags whatever the caller passes, and rebuilds association terms from the final tag list. A "not X" teaching therefore also removes X, and its search terms, from near-copies (cosine ≥ 0.85) on the next re-tag. Per-meme rejections veto machine tags only: tagging X by hand withdraws an earlier "not X" on that meme, and re-tagging never drops a hand tag. A re-tag pass cut short (the seven-minute session limit, Stop) is resumed with the memes it hadn't reached the next time it runs, while labels and teachings stay the same; a change to either starts over, and a change while a pass runs sends it round the library again for the memes it did before the change. A meme whose tags come out the same is not written again.

### Bundled labels and text embeddings

Bundled labels (`assets/knowledge/label-prompts.json`) tag a meme by zero-shot prompts: a label applies when the cosine between the meme's image vector and its prompt's text vector, less half the closest of the bundled "ordinary picture" anchors, is 0.13 or more, and a meme keeps at most six machine tags. Prompts and search queries are tokenized in Kotlin (`inference/ClipTokenizer.kt`) from the pinned tokenizer.json, with CLIP's start and end tokens, and reach the text model as ids. Before, the runtime's C++ tokenizer did this, and its ids made every text embed within a median cosine of 0.98 of every other: replaying one library's 2,344 memes with the label vectors an install had cached, not one meme reached the tag threshold, and semantic search ignored the query's words. With the Kotlin ids, the app's text model gives the vectors of open_clip's MobileCLIP-S2 (cosine 1.000000 for 60 label prompts, run on a Mac), and the same replay tags 1,743 of the 2,344 memes. For example, the prompt label "patrick bateman" lands on 45 of the 51 memes the owner labeled so and on 3 of 536 memes he labeled otherwise; "spongebob" on 12 of 17 and none of 570. Label vectors are encoded again once, on first use after the update (cache version MGL3). Caption vectors stored before the fix are left as they are; a caption made again gets a new one. How much the old ones still count in search was measured on one sample, not proven: on the Pixel 5a, 156 of 527 stored caption vectors came from the old tokenizer (each sits under cosine 0.5 to a new embedding of its own caption text). Against 1,113 test queries embedded the new way they reached at most cosine 0.62, and 160 of those 173,628 query-caption pairs passed the caption floor of 0.55, so they can still move a few results a little. Their caption text stays searchable.

### TV shows and movies

170 of the bundled labels are TV shows (category `tv`, 81 titles, cartoons and anime included) and movies (`movie`, 89). The tag dialog offers both categories, and the viewer shows a title as "(TV show)" or "(movie)". A meme gets at most one title (`knowledge/Titles.kt`):

- A person's label that names a title gives the meme that title. A label names a title by its name, one of its other names ("sopranos", "madmen", "dbz") or a character only it has ("tony soprano", "patrick bateman"). Case, accents, apostrophes and spaces don't matter, nor does a leading "the" before two or more words ("walking dead"); before one word it does, so "office", "mask" and "whale" stay everyday words, not The Office, The Mask and The Whale. Other names that also name something else are left out: another show or film ("avatar", "blade runner", "terminator"), a franchise or studio ("marvel", "ghibli"), a real person seen elsewhere ("gordon ramsay"), a character from another listed title ("saul goodman", "heisenberg") or an everyday word ("drive", "got"). The 2019 film is "Joker (2019)", because the Joker is also in The Dark Knight. An exact copy (cosine ≥ 0.985) of a meme or teaching labeled so gets the title too, unless a "not" example lies within cosine 0.85.
- A "not" answer or a rejection counts against a title only when it names the title itself, by its name or another of its names: "not tony soprano" says nothing about the show. It rules the title out on that meme, where the next title can then win, and a "not" example within cosine 0.85 rules it out on a near-copy.
- Otherwise the titles compete on their prompts ("a scene from the TV show The Sopranos", "a scene from the movie American Psycho"): the best applies at an anchored margin of 0.17 or more and 0.02 ahead of the next title, because similar art styles and actors pull a picture toward several titles at once. Other labels need 0.13.
- A title learns from people's labels once its examples hold up, as labels do for the look-alike vote: each labeled meme is judged with its own examples and copies left out, and a title needs at least 3 picks that its examples made, 90% of them right. A learned title adds 0.3 × (nearest example's cosine − 0.55) to its prompt margin when that margin is at least 0.10 and no "not" example lies nearer.
- The Label tab asks "From the sopranos? (TV show)" when one title stands out for a meme (margin 0.15, 0.01 ahead, with every title's examples counting) and no person gave the meme a title. Yes and Not this become the examples and counter-examples titles learn from. A suggested label of the person's that names a title is asked as that title ("From sopranos? (TV show)"), and the bundled question is then not asked as well. Title questions wait until the label vectors are at hand; right after an update, until indexing or a re-tag has encoded them, the tab asks about people's labels alone instead of waiting minutes for the text model. A typed answer that names a title by name is filed as that TV show or movie; a character's name keeps the category people gave it.

A meme carries its title once. A person's own tag that names the title by its name or another of its names stands for it, and the next re-tag files that tag as the TV show or movie, unless the person already chose one of those; a character's name ("patrick bateman") stays a tag of its own, with the title beside it. When the vote spreads a person's label that names the title, that tag takes the title's category instead of standing beside it, and the title takes the place of an older topic label of the same name ("spongebob", "star wars"). Titles that in testing mostly attracted unrelated pictures (any anime girl, any muscular cartoon, any talk-show desk, people of one skin color or hair color) are left out, as are titles that are also everyday words ("It", "Friends", "Get Out"). Titles are not offered to the optional cloud judge, which is asked for a format or character.

Measured offline on one 2,344-meme library with its owner's labels and teachings. A numpy copy of the rule and the Kotlin code gave the same title, or none, for all 2,344 memes, and the same held-out record. 176 memes get a title: 101 from his own tags that name it, which now stand for it, 10 from a character's name or an exact copy, and 65 picked, of which 53 are right, 9 wrong and 3 unclear by eye. Keeping characters apart from a title's other names, and dropping names that also name something else, changed none of these 176. Two of his titles have learned so far: American Psycho (18 held-out picks, all right) and SpongeBob (8 of 8). Shrek's two examples pulled in green Pepe pictures (0 of 3), so it stays unlearned. On the 132 memes whose title is known from his labels or a test set's answers, with each meme's own examples and copies left out, examples raise the right titles from 44 to 71; examples closer than cosine 0.985 stay in, so near-copies of a labeled picture count toward that number. On memes nobody labeled, learning added 4 titles, all right. The thresholds were chosen on these same memes, so expect lower precision elsewhere. A show that isn't on the list draws the closest one that is (a frame from another Pixar-style film was tagged Ratatouille). Memes indexed before the update get titles at the next re-tag (**Settings → Re-tag All**, or leaving the Label tab after an answer).

## Optional cloud assistance

Cloud assistance, automatic escalation and media/transcript consent are **off by default**. Configure them in Settings only if wanted. There are separate adapters for hosted Typesafe System One/JEV, Cloudflare Clef/Clef-flash, and an HTTPS self-hosted System One-compatible service. JEV is a decision model here, not JEPA and not a resident phone model. Optional captions use a separately configured OpenAI-compatible HTTPS endpoint.

Text-state consent can disclose OCR or caption content; it is not anonymous. Visual consent allows at most two stripped, resized frames. Transcript consent is separate. Filenames, local paths and embeddings are not ordinary request fields. Enabling automatic escalation applies to new uncertain items; including the existing backlog requires a separate opt-in.

Provider probabilities describe a provider's choice distribution, **not measured identification accuracy**. Cloud suggestions retain source, score domain, review status and provenance. They do not become manual labels or training examples merely because the provider was confident. Explicit acceptance creates a human-reviewed teaching while keeping its cloud origin. Rejection persists a veto and removes the corresponding weak prototype.

Saved cloud observations can improve offline retrieval without retraining a large model: a bounded local vector memory supplies explicitly unreviewed `cloud_hint` candidates for similar content. Captions are not copied onto similar images with different text. Disabling cloud stops future requests but keeps saved evidence for offline use. **Forget cloud** removes unreviewed observations and weak memory while retaining human-confirmed teachings and rejections.

Credentials are encrypted using Android Keystore. Cloud configuration, consent, credentials, request bookkeeping and caches are excluded from OS backup/transfer. No ambient development-agent credentials are used.

## Resource and network limits

- One inference family at a time; primary image/text encoders share a family. Heavy optional captions, speech and DINO enrichment are disabled by default.
- Core MobileCLIP-S2 plus English CRAFT/CRNN OCR artifacts need about 420 MiB. DINO, Whisper small.en (int8, 429 MiB with its tokenizer) and FastSAM bring the encoder and helper models to about 1.2 GiB.
- Candidate verification uses a bundled 337 KiB FP16 Siamese visual verifier (`assets/knowledge/pairwise_verifier.bin`, 64-d penultimate features paired with the C++ Positive-Unlabeled residual head `OnDeviceDecisionHead`) across both initial indexing and `Re-tag All`, replacing the retired 407 MiB `d1-omni` GGUF and purging any leftover copy on launch. `open_vocab_concepts.bin` (6,028 concepts, 12.5 MiB) strips personal-library reference vectors and adds anti-hubness-centered reaction prototypes. Speech batches run `AudioVad` voice-band + syllabic modulation compaction before loading Whisper and skip video frame decoding; video indexing sweeps a single sequential `MediaCodec` pass (`VideoFrameExtractor.extractMultiple`) and caches distinct scene frames for caption/DINO reuse; captions skip verbatim `TEXT:` regurgitation (`maxTokens = 112`) when OCR is already captured.
- Local AI captions use MiniCPM-V 4.7 1B on the CPU through llama.cpp b11588, pinned in `runtime/bootstrap.sh`. The first caption downloads a 641 MiB Q4_K_M language model and a 1.03 GiB vision projector, both pinned by size and SHA-256. The projector ships as BF16, which ARMv8.2 CPUs such as the Pixel 5a's only run through a slow fallback, so the app converts it once to F16 (99.97% of values unchanged; none above 1e-3 change), checks the result against its own pinned SHA-256 and deletes the BF16 file. Disk use is about 1.7 GiB after that, 2.7 GiB during the conversion.
- Captions scale each image or video frame to at most 448×448 pixels, so a frame needs one vision encoder pass; videos use up to three frames, and a frame that looks the same as an earlier one (at most 0.1% of a 128×128 grid's pixels changed by more than 40 of 255 in red, green or blue) is captioned only once: of the first 265 videos captioned on the 5a, 69 got the same caption from all three frames. In the app on the Pixel 5a (cooled down, on battery), each frame took 15–24 s with 2 threads: vision 7.6–11 s, prompt 4.4–7 s, reply 3–7.6 s. A command-line build of the same runner took about 4 s to load and 15–17 s per image. Memory was about 2.1 GB (PSS) while captioning and about 280 MB after the session. One seven-minute session captioned seven memes, most of them three-frame videos. Each caption and transcript is saved as soon as it is made. After seven minutes a session starts nothing new, but the caption or transcript in progress may finish, up to 9.5 minutes in all; Stop repeats only the meme in progress. A background session on the 5a is much slower than the open app: the library's 232 s clip (120 s of audio; a two-minute clip took 143 s in the app) was still unfinished after 8 minutes there, and since cut-off work went back to the front of the queue, nothing after it ran. A clip that a background session's hard stop cuts off after a whole session's time is now left for a session started in the app (**Index**, or Settings → Transcribe), and background sessions carry on with the rest. The app uses the faster cores only: 2 threads on the 5a, at most 4 elsewhere. 4 threads on the 5a were no faster: over 12–13 frames each, in the open app on the charger, vision took 8.6 s per frame against 8.5 s, and prompt and reply ran 5–10% slower per token. With the original BF16 projector the vision step alone took 66–101 s. A second 1.8 GB process beside the phone's other apps is too much for the 5a: twice a command-line caption run there was followed by Android's system process restarting and wireless debugging dropping.
- The caption prompt puts the fixed instructions before the image and the meme's own hints after it, and the runner keeps the model's state after the instructions (234 tokens with the system prompt) from one caption to the next. MiniCPM-V 4.7's language model (`qwen35`) has recurrent layers, so the state is saved and restored whole rather than cut back to a position. On the Pixel 5a the prompt step went from about 4.9 s to about 1.5 s per frame (24 frames, logged as `reused_tokens`). The image and reply steps were slower in the same run, with the phone's memory nearly full and swapping, so the frame rate that day stayed about 22 s. An interleaved run on a Mac with the app's runner and model files (2 threads, 8 rounds each) showed the image step unchanged by the reuse (7.7 s against 7.6 s) and the prompt step down from 2.2 s to 0.4 s, and a reused caption came out byte for byte the same as one from a fresh context. Before the change, 16 of the owner's memes were captioned both ways on a Mac with the app's prompt, sampler and model files: the new order kept all 16 replies in the four-line format (15 of 16 before), read slightly more of the on-screen text (0.69 against 0.52 of OCR words, 6 memes with text) and named about as many of the owner's labels (28 against 27 of 148), with one terser caption among the 16.
- Caption sessions keep the caption model loaded. Search vectors for a session's captions are made once, when it ends; making them after every batch of eight unloaded and reloaded the 1.7 GB model each time (about 29 s a batch on the 5a), and memes waited a further 1.2 s each for no reason. The same end-of-session step makes up to 200 vectors an earlier session never wrote (96 captions on the 5a had none). On the charger, **Caption now** and its siblings, and background sessions that got their foreground service, run for an hour instead of seven minutes, since each session boundary cost about 75 s there. A caption or transcript is marked failed while it runs, so a native crash can't loop; when the app is killed instead (an install, a force-stop, Android reclaiming memory), the next session gives the meme one more try, and only a second kill leaves it failed with an error. Before this, 45 of the 5a's 46 failed captions were such kills with no error. The runner logs `total_ms` for the whole call beside its steps.
- Captions never hold up indexing. Indexing batches skip the caption step; captions are written afterwards for already-indexed memes, a batch at a time, until the session ends. A session started with **Index** captions only once its indexing queue is empty; a background run indexes up to 32 memes and then spends its remaining time on captions. On the Pixel 5a that is about 20 s per image and about a minute per video, so a library of a few thousand memes needs many sessions; with background processing on, they run back to back while the phone charges, so the backlog finishes without tapping **Index**. **Caption now**, **Transcribe now**, their **Retry failed** buttons, **Redo all transcripts** and **Run Pending** do the same from the app: on the charger, each session that got something done is followed at once by the next, until no work is left, the phone is unplugged or **Stop** is tapped; on battery they run one session. While captioning or transcribing, the progress card and Settings show how many captions or transcripts the library still needs ("Captions: 1275 left"), and the bar shows the library's share done. A run that stops at once, such as on battery below 20% with **Pause on low battery** on, a warm phone or a model that can't be fetched, says why under **Captions & Transcripts** ("Last run stopped: Paused for low battery"); on the owner's Pixel 9 at 10% battery, **Caption now** looked like it did nothing until the phone was plugged in.
- Speech uses Whisper small.en, the int8 XNNPACK export from the model tag that react-native-executorch 0.9.2 loads. tiny.en, used before here and in the original app, turned a laughing South Park line, "No, dude, no fucking way", into "No, no, no, sucky way."; small.en gets it word for word, as whisper large-v3-turbo does. On 15 English-speech clips from the owner's library, scored against large-v3-turbo with this app's decoder and `.pte` files on a Mac, word error rate was 22% for tiny.en, 17% for base.en int8 and 13% for small.en int8, then 11.5% once a window that the model ends early, or that runs out of its 128 decoder positions mid-segment, carries on from the last finished segment instead of jumping 29 s. The original app's stored transcripts scored 38% on the same clips. small.en costs more than tiny.en; its decoder steps cost about 4 times as much. On the Pixel 5a it took 31.9 s for the 29.5 s South Park clip (5.1 s encoding, 46 decoder steps of about 0.5 s) and 143 s for a two-minute clip. Each clip's timing is logged under `MemegetWhisper`.
- After a speech-model change, the next session with Audio Transcription on marks every video for transcription once (setting `audio.model`), in one transaction that changes only the audio state. The old text stays searchable until the new model replaces it, and the retired model files are deleted. After indexing, a session transcribes waiting videos before it captions anything: with captions first, the rest of a seven-minute session on the 5a transcribed no videos and captioned one meme; with transcripts first, the next session transcribed nine videos, about 9 per session, so the owner's 447 videos need about 50 sessions.
- Indexing uses batches of 32 and seven-minute coroutine sessions, preserving pending work on cancellation. A single native kernel cannot be interrupted midway; this is not a hard process-kill deadline. Heavy enrichment pauses at a moderate thermal state (**Pause when device is warm**) or on low battery.
- Stopping a session, its seven-minute limit, or leaving the screen whose search or tool started a download is not an error: the partial file stays and resumes. Sessions started from a screen (the startup session and **Run Pending**) belong to the coordinator, so leaving the screen or an activity restart doesn't stop them. A model that can't be downloaded or prepared (offline, a server error, a failed integrity check) pauses the work that needs it for the rest of that session instead of failing item after item: memes stay queued, transcripts and captions go back to waiting, and the model is reported once under **Recent Indexing Errors** and in the session's status line.
- Background processing runs a session when the app opens and every 30 minutes (Android picks the exact time). While the phone charges, a background session that got something done queues the next one 30 s after it ends, until no work is left or the phone is unplugged. If the phone is warm at that point, the next one starts after five minutes instead; if it is still warm then, it pauses until the 30-minute run. Progress counts tasks, not memes, so a video that got its transcript but still waits for its caption counts. The background switches in Settings reschedule the work at once.
- Android 12 and later refuse a foreground service to an app in the background unless its battery use is **Unrestricted** (Settings → Apps → Memeget Native → App battery usage → tap the words **Allow background usage** → **Unrestricted**). Without it a background session still runs, but with the screen off Android keeps the app on its slowest cores; on the Pixel 5a that made transcription several times slower, and a long clip could not finish within a session. With **Unrestricted** a session keeps its foreground service and the faster cores, with the screen off too.
- Sessions started from the app keep it alive with a `dataSync` foreground service. Android 15 and later allow those six hours in the background per 24 hours (opening the app resets it), and kill an app whose service doesn't stop at the limit. The service stops itself when Android calls its timeout, and also when a start is refused because the six hours are spent. The session in progress then stops as **Stop** would, putting the meme it was on back in the queue, and a background session is queued to carry on while the phone charges (background processing on). Host tests cover the timeout and the hand-over; a phone or emulator on Android 15 or later has not exercised it yet.
- Thumbnail disk cache: 128 MiB. Search uses bounded vector batches/cache and bounded result selection rather than an all-library sort in memory.
- Weak cloud memory: at most 2,048 vectors of 512 floats, eight per label, 30-day expiry, and an 8 MiB serialized ceiling. Rejections are retained conservatively; saturation disables weak-memory growth rather than resurrecting discarded claims.
- One cloud request in flight. Complete serialized requests are limited to 1 MiB; responses to 64 KiB. Defaults: 20 requests, 10 MiB and an estimated $0.05 per day, normally on unmetered networks.
- Consent is rechecked before sending and before persistence. Revocation cancels in-flight work and rejects late results. Cancellation cannot recall bytes already sent. No automatic retries, redirects or implicit provider fallback. Uncertain delivery consumes its conservative reservation.
- The local cost ledger is an estimate. Configure a provider-account spending cap for a hard monetary limit.

Fixed after the pass, each checked again on the phone: a look-alike video kept the previous clip's frozen picture while the new one played unseen; a clip kept playing after leaving the app; editor taps were dropped while a video played; switching tabs reset the Library's search, scroll position and dismissed install note; the keyboard came back after closing a meme opened from search; during a re-tag a search never finished (94 s with no results) and a deleted meme stayed in the grid; and a meme shared while a session transcribed waited for a later session. Still open: the semantic pass reorders text matches about 2 s after they show on a release build (5 s on debug); each share opens a fresh Library in the sending app's task, blank for 0.6–2 s while it loads; a VP9 profile 1 (4:4:4) WebM can't be decoded by the 5a's hardware decoder and nothing falls back to the software one (profile 0 and VP8 are fine); and while text is typed on a video the preview player is rebuilt about every 250 ms.

Also open for identification: 1,613 of that library's 1,752 unlabeled memes have no labeled look-alike at cosine 0.80, so the vote cannot label them; search reaches them only through their text and picture similarity.
